> 本文件记录「素材怎么来的、怎么加工、以后用户自传照片怎么做」，避免下次重新试错。

## 一、素材清单

| 文件 | 位置 | 用途 |
|---|---|---|
| `stage1.png` … `stage5.png` | `健身网站/assets/characters/` | 网页用的透明底角色（400px 高） |
| `stage1@2x.png` … | 同上 | 2 倍图（800px 高） |
| `角色风格A-3D卡通手办风.png` | `健身知识库/角色形象/` | 风格母版（带灰底、无水印），生成新阶段时的参考图 |
| `成长序列-上线效果预览.png` | 同上 | 5 阶段在绿色卡上的效果预览 |

阶段与等级对应（`src/pages/home.js` 的 `CHAR_STAGES`）：

| 阶段 | 等级 | 形象特征 |
|---|---|---|
| stage1 新手 | 1+ | 匀称偏瘦，几乎没肌肉线条 |
| stage2 入门 | 20+ | 肩臂有轻微线条 |
| stage3 规律 | 45+ | 明显肌肉：肩、胸、二头，V 型躯干 |
| stage4 硬核 | 70+ | 强壮厚实，脖子搭毛巾 |
| stage5 练不虚 | 95+ | 最强形态，背宽臂粗 + 金色描边/暖金轮廓光 |

> 观察到的现象：宽高比从 0.482 递增到 0.645。这不是裁切误差，是**肌肉变宽**的真实体现——
> 所以 CSS 必须固定**高度**（`.hero-av { height:204px }`）、宽度自适应，否则换阶段时角色会忽大忽小。

## 二、生成方式（已验证）

用**图生图**（image-to-image）保证是「同一个人在不同阶段」，而不是 5 个不同的人。

**生成某个新阶段**：
```
输入图：① 角色风格A-3D卡通手办风.png（身份锚点，永远带上）
        ② 上一个阶段的图（保证是连续成长）
提示词模板：
  Same exact character and art style (3D cartoon Pixar-like render).
  Keep the same young Chinese man's face, same short black hair, same green tank top,
  dark grey shorts, black sneakers. Now at a <阶段名> training stage: <体型描述>.
  Same solid light grey background, same lighting, standing full body front view, centered.
质量：high ｜ 尺寸：1024x1024
```

**体型描述用词**（递进关系，别跳档）：
- 入门：`slightly leaner and a bit more defined than a beginner, visible light muscle tone`
- 规律：`clearly more muscular — defined shoulders, visible biceps and chest, athletic V-taper`
- 硬核：`strong thick arms, broad shoulders, clearly built, a small white towel around his neck`
- 练不虚：`peak powerful physique, wide back and thick arms, golden trim + warm golden rim light`

## 三、加工成网页素材（必跑）

```bash
cd 健身网站
python3 tools/make-character.py <输入图> stageN --ref "健身知识库/角色形象/角色风格A-3D卡通手办风.png"
```

脚本干三件事（都是可复现的数值规则，不是手调）：
1. **裁掉右下角「AI生成」水印**（生图固定打在右下角；按参考图尺寸对齐后切掉右下 15%×2.5%）
2. **抠透明底**：四角估背景色 → 从四边洪泛「颜色接近 + 中性灰」→ 再吃浅中性灰地面阴影
   （亮度区间刻意排除深色鞋 mx≈50 和亮白鞋底 mx≈245）
3. **按 alpha 实际边界裁紧**，统一导出 400px / 800px 高

> 注意：`assets/` 会被 `node build/build.js` 自动拷到 `dist/assets/`，不需要手动传。

## 四、用户自传照片 → 3D 角色（已跑通，待接后端）

### 实测的两种做法与取舍

| | 方案① 照片 + 风格参考图 | 方案② 只用照片 + 风格描述 |
|---|---|---|
| 风格统一度 | **高**（和标准角色一套） | 中（偏游戏半写实） |
| 和本人相似度 | 弱（容易被参考图"带跑"成标准脸） | **明显更强** |
| 结论 | 适合「统一世界观」 | 适合「这就是我」 |

**建议的最终做法**：方案② 为主 → 若风格不够统一，再补一次「风格强化」的第二遍生成（而不是一开始就喂参考图）。
把这两个方案的样张留档在 `角色形象/照片转3D角色-两种方案对比.png`。

### 产品化时必须处理的四件事（都是钱和合规）

1. **这是付费功能，且要限流**：每张图有真实成本（生图 API 按张计费），
   建议「年费会员每月 1 次 + 额外次数单独付费」，避免被白嫖。
2. **内容审核**：用户上传人像 = 上传个人信息。
   - 上传前必须让用户勾选授权（"我确认这是本人照片，同意用于生成形象"）
   - 生成结果要有举报入口（万一被传了不当照片）
   - 照片**生成完即删**，不要长期留存原图
3. **隐私与合规**：人像属于敏感个人信息，小程序/网站的隐私政策要单独列一条；
   个人主体小程序对这类功能审核偏严，建议先在**网页版**上线（不受小程序类目限制）。
4. **技术链路**：
   ```
   网页（<input type=file> 压缩到 ≤1MB）
     → 云函数 uploadAvatar（校验大小/格式，转存临时地址）
     → 云函数 genAvatar（调用生图 API，img2img，带风格提示词）
     → 拿到结果图 → 走 tools/make-character.py 同一套抠图逻辑（Node 版需另写）
     → 存 CloudBase Storage → 用户的 player.avatar 指向它
   ```
   ⚠️ 抠图这一步目前是 Python 脚本，云函数里要用就得移植成 JS（numpy 部分可用 `sharp` + 手写洪泛）。

### 优先级建议

**排在 M4（俯卧撑识别）之后**。原因：它是**锦上添花**，而账号、工具同步、游戏化闭环是**必需品**。
等有一批会员真的在用、愿意为"专属形象"额外付费，再投入做后端链路。
